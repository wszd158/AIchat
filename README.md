# 🤖 AI 对话系统 (AI Chat System)

> 一个多角色 AI 对话系统，支持本地模型部署和智能对话管理

## 📖 项目简介

**AI 对话系统**是一个基于 Streamlit 构建的多角色 AI 对话平台，允许用户配置多个 AI 角色进行自动化对话。系统支持本地大语言模型（如通过 LM Studio 部署的模型），具备长期记忆管理、对话提炼和智能主持人等功能。

该项目专为研究多 AI 代理交互、角色扮演对话和复杂对话管理而设计。

## ✨ 核心功能

* **👥 多角色对话**：支持配置多个 AI 角色，每个角色拥有独立的人设和参数
* **🧠 长期记忆机制**：通过提炼员定期生成对话摘要，作为长期记忆注入后续对话
* **🕵️ 智能提炼员**：可配置幕后提炼员，自动总结对话内容并防止信息丢失
* **🎭 主持人模式**：支持显式主持人角色，引导对话方向
* **💾 配置管理**：基于 JSON 的配置文件管理，支持多套配置方案保存和切换
* **📜 对话历史**：完整的对话历史记录和存档功能
* **🛡️ 防死循环机制**：内置多重保护机制，防止提炼员和角色间产生死循环
* **🔌 本地模型支持**：完美兼容 LM Studio、Ollama 等本地 LLM 运行环境

## 🛠️ 技术栈

* **Python 3.8+**
* **Streamlit** - Web界面框架
* **OpenAI Python SDK** - 连接本地或远程模型API
* **JSON** - 配置和历史数据存储

## 🚀 快速开始

### 1. 环境准备

确保已安装 Python 3.8+。Windows 用户可以直接双击运行 `chat_arena.bat` 启动脚本，该脚本会自动检测 Python 环境并安装必要的依赖。

对于手动安装，可以使用以下命令：

```bash
pip install streamlit openai httpx
```

### 2. 配置本地大模型（可选）

推荐使用 **LM Studio** 部署本地模型：

1. 下载并安装 [LM Studio](https://lmstudio.ai/)
2. 在 LM Studio 中加载模型并启动服务器
3. 默认地址：`http://localhost:1234/v1`
4. API Key 通常可任意填写（如 "lm-studio"）

### 3. 运行系统

增强版启动脚本功能：
* 自动检测 Python 环境
* 自动安装缺失的依赖包
* 提供清晰的错误提示

```
streamlit run chat_arena.py
```

或者使用项目提供的批处理文件（Windows）：
```
chat_arena.bat
```

启动脚本会自动检测 Python 环境和依赖包，如未安装会自动安装所需依赖。

## 🎛️ 核心组件

### 角色配置
- **角色 A/B**：两个主要对话角色，可自定义名称、模型、人设等
- **主持人/提炼员**：可切换模式的角色，支持两种工作方式：
  - 📢 显式主持人：直接参与对话
  - 🕵️ 幕后提炼员：后台生成对话摘要

### 控制参数
- **最大轮数**：限制对话总轮数
- **上下文记忆数**：控制传递给模型的上下文长度
- **介入频率**：主持人/提炼员介入对话的频率
- **自动播放速度**：自动模式下的对话速度

## 🎭 运行机制详解

可以把整个系统想象成"两个演员和一个后台记录员"在演戏，但他们彼此不见面，分别关在不同的房间里。

核心逻辑是：**每次轮到谁行动，系统就给谁临时搭建一个专属的"房间"（构造专属的上下文）**。

### 第一阶段：角色 A 发言 (The Actor A)

当轮到 **角色 A** 说话时，程序执行以下步骤：

1. **清场与搭建 (Backend Logic)**：
   * 系统取出所有的聊天记录。
   * 系统把 **角色 B** 以前说过的所有话，全部贴上标签 `[User]: [角色B]: ...`。
   * 系统把 **角色 A** 自己以前说的话，标记为 `[Assistant]: ...`。
   * 系统把 **长期记忆**（如果有）写在一张纸条上，贴在墙上（System Prompt）。

2. **进房演戏 (LLM Action)**：
   * 模型（LLM）进入房间。
   * **它看到的剧本是**："我叫角色A（System），我对面有一个叫角色B的人类（User），我们已经聊了这么久（History）。墙上贴着前情提要（Memory）。"
   * **模型的反应**：它完全不知道"角色B"其实也是个AI，它只觉得自己在回复一个用户。
   * 它生成回复："你好，B先生。"

3. **存档**：
   * 系统把这句话存入公共数据库 `st.session_state.messages`，标记为 `Role: A`。

### 第二阶段：角色 B 发言 (The Actor B)

紧接着轮到 **角色 B** 说话，系统**重新搭建**了一个完全相反的房间：

1. **清场与搭建 (Backend Logic)**：
   * 系统再次取出所有聊天记录（包含刚才 A 说的那句）。
   * **视角反转**：这次系统把 **角色 A** 说的话（包括刚才那句），全部贴上标签 `[User]: [角色A]: ...`。
   * 系统把 **角色 B** 自己以前说的话，标记为 `[Assistant]: ...`。
   * 系统把 **长期记忆**（同一张纸条）也贴在这个房间的墙上。

2. **进房演戏 (LLM Action)**：
   * 模型（LLM）进入房间。
   * **它看到的剧本是**："我叫角色B（System），我对面有一个叫角色A的人类（User），他刚才跟我打招呼了。"
   * **模型的反应**：它根据自己的人设（比如它是程序员），回复道："Hello world，A。"

3. **存档**：
   * 系统把这句话存入公共数据库，标记为 `Role: B`。

### 第三阶段：提炼员工作 (The Secret Recorder)

假设对话进行了 5 轮，触发了"提炼员"时刻。提炼员**不参与对话**，他是像上帝一样在云端看着。

1. **打包资料 (Backend Logic)**：
   * 系统把最近 20 条对话记录，直接打印成一份纯文本文件（String）。
   * 格式像这样：

```
[角色A]: 你好。
[角色B]: Hello World。
...
```

2. **下达任务 (Prompt Injection)**：
   * 系统给模型发了一个**独立任务**，不加载任何 User/Assistant 的对话历史。
   * **指令是**："你是一个记录员。请阅读下面这份文本，总结他们的共识和冲突。" + `[刚才打印的文本]`。

3. **生成记忆 (Memory Update)**：
   * 模型阅读文本，生成一段摘要："A和B互相问候了，目前气氛融洽。"
   * **关键点**：这段话**不**发给用户看，而是**覆盖**掉之前贴在墙上的那张"长期记忆"纸条。

### 闭环：下一轮 (Next Round)

当再次轮到 **角色 A** 说话时：

* 他走进房间，发现墙上的"长期记忆"纸条变了，上面写着："A和B互相问候了..."。
* 于是 A 就会基于这个最新的记忆继续聊天，不会忘事。

### 总结流程表

| 步骤 | 执行者 | 它的视角 (System) | 它眼中的历史 (Messages) | 结果 |
| --- | --- | --- | --- | --- |
| **1** | **角色 A** | 我是 A | 别人全是 User，我自己是 Assistant | 生成新回复，存入历史 |
| **2** | **角色 B** | 我是 B | 别人全是 User，我自己是 Assistant | 生成新回复，存入历史 |
| **...** | (循环) | ... | ... | ... |
| **N** | **提炼员** | 我是记录员 | (无历史，全是文本素材) | **更新后台记忆变量** |
| **N+1** | **角色 A** | 我是 A (+新记忆) | 别人全是 User | 基于新记忆继续聊 |

### 主持人和提炼员的区别

虽然它们在业务逻辑上很特殊（一个管节奏，一个管记忆），但在**底层调用**上，它们依然遵循我们定义的"相对视角"规则。

#### 1. 显式主持人 (Active Moderator)

**场景**：他是一个实实在在的角色（比如辩论赛主席、跑团DM），他会直接在聊天框里说话，所有人都看得到。

**工作原理（相对视角）**：

* **他的视角**：我是 `Assistant`，角色A和角色B都是 `User`。
* **输入**：`messages`: 完整的对话历史（包含了 A、B 之前的发言，也包含了他自己以前的发言）。
* **行为**：他看到 A 和 B 吵得不可开交，或者剧情卡住了，于是决定发言。
* **结果**：生成的回复直接 append 到 `st.session_state.messages` 显示给用户看。

#### 2. 幕后提炼员 (Background Refiner)

**场景**：他是一个"幽灵"，用户看不见他。他默默阅读之前的对话，总结出"长期记忆"，然后写入后台变量，不发消息。

**工作原理（God View / 上帝视角）**：

* **他的视角**：虽然调用的是同一个函数，但我们通常采用**"Prompt 注入"**的方式。因为提炼员不需要参与对话流，他只需要完成一个"阅读理解"任务。
* **特殊处理**：我们通常**不**把 `st.session_state.messages` 传给 `generate_reply` 的 `messages` 参数，而是把历史记录拼接成字符串，直接塞进 `override_system`（覆盖系统指令）里。
* **结果**：生成的 `raw_summary` **不** 放入消息列表，而是存入 `st.session_state.long_term_memory`。

## ⚠️ 常见问题与排查 (Troubleshooting)

### Q1: 对话角色顺序混乱或报错

**原因**：对话历史中的角色顺序不符合预期，通常是由于手动修改历史记录或程序异常导致。

**解决方案**：
* 系统已内置安全气囊机制，自动检测并修复连续的用户消息
* 避免手动修改对话历史文件

### Q2: 提炼员陷入死循环

**原因**：提炼员生成的内容触发了新一轮提炼请求。

**解决方案**：
* 系统已实现多重防死循环机制：
  * 最大轮数限制（默认3次）
  * 内容收敛检测（相似度>95%时停止）
  * 精确的触发条件控制（仅在角色B发言后触发）

### Q3: 配置无法保存或重置

**原因**：UI组件未正确绑定配置值。

**解决方案**：
* 系统已修复SelectBox组件的索引绑定问题
* 现在可以正确保存和加载配置
